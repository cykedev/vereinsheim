**TL;DR** Entschieden mit dem User am 26. und 27. Oktober 2026. Ein Vorhaben aus mehreren Teilplänen läuft
koordiniert: Eine koordinierende Session im Haupt-Checkout plant jeden Teil über `/plan`, führt einen
Koordinationsplan als Ledger, spricht als einzige mit dem User und übernimmt fertige Branches. Jeden freigegebenen
Teilplan setzt eine Kindsession in einem eigenen Worktree um (`/implement → /validate → /review`) und meldet sich nur
bei der koordinierenden Session. Eine einzelne Änderung bleibt PIV in einer Session. Ablauf: Skill `/coordinate`.

## Kontext

PIV ([[adr-018]], [[adr-020]], [[adr-023]]) ist auf eine Änderung in einer Session zugeschnitten: ein Plan, ein Branch,
ein Lauf. Ab dem 26. Oktober 2026 lief das Vorhaben aus [[adr-033]] (Treffsicher geht in Spiegel auf) als Folge vieler
Teilpläne, teils nacheinander, teils parallel, mit Teilen für `main` und Teilen, die nur zusammen live gehen können.
In einer einzigen Session wäre das schwer geworden: Der Kontext läuft über Erkundung, Code und Gate-Ausgaben voll, und
parallele Teile brauchen getrennte Arbeitsbäume.

Ausprobiert wurde deshalb eine Aufteilung in Rollen: Die Hauptsession plant und koordiniert, Kindsessions bauen. Die
Regeln entstanden im Koordinationsplan des Vorhabens (Abschnitte „Branches“, „Regeln für Kindsessions“,
„Grundsätze“). Der User will diesen Modus als Standard für jedes Vorhaben dieser Art. Diese ADR hält ihn allgemein
fest.

## Entscheidung

### 1. Wann

Koordiniert läuft ein Vorhaben, das aus mehreren Teilplänen besteht (wie [[adr-033]]). Eine einzelne Änderung, auch
eine große, bleibt PIV in einer Session. Der Modus ist eine Ebene **über** PIV: Jeder Teil läuft weiter
`/plan → /implement → /validate → /review`, nur auf zwei Sessions verteilt.

### 2. Die koordinierende Session

Die Hauptsession arbeitet im Haupt-Checkout, ohne eigenen Worktree, auf dem Basisbranch des Vorhabens. Sie baut
selbst keinen Code.

1. **Planen.** Jeden Teil plant sie über `/plan`. Die Erkundung gibt sie an Sub-Agents (Explore, Plan), damit ihr
   eigener Kontext über das ganze Vorhaben schlank bleibt.
2. **Koordinationsplan als Ledger.** `plans/<datum>-<thema>.md` mit Grundsätzen, Branches, Regeln für Kindsessions,
   den Teilen und einer Tabelle „Stand“ (Teil, Plan, Branch, Session, Stand). Sie hält ihn nach jedem Schritt aktuell.
3. **Einzige Stimme zum User.** Ideen des Users prüft sie kritisch (Urteil, Risiken, Gegenvorschlag). Technische
   Fragen der Kindsessions entscheidet sie selbst, fachliche gibt sie an den User weiter.
4. **Kindsessions starten.** Nur auf eine Nachricht des Users hin, sonst schlägt sie die Session als Karte vor. Jede
   Kindsession bekommt einen vollständigen Auftrag (Einrichtung, Arbeitsweise, Abschluss, Aufräumen), denn sie kennt
   nur diesen.
5. **Geschützte Pfade** ([[adr-023]]): Den Diff prüft sie, bevor die Kindsession ihn committet.
6. **Branch übernehmen.** Einen fertigen Branch prüft sie selbst: Fast-forward möglich, Gate im Worktree mit der
   richtigen Node-Version (über `git -C` oder eine Subshell, nie per `cd` hinein), keine Personendaten im Diff
   ([[adr-029]]), Migrationen additiv. Nach `main` merged sie nur mit OK des Users, ff-only (`git fetch . <branch>:main`,
   wenn `main` nirgends ausgecheckt ist). Danach zieht sie den Basisbranch sofort per `git rebase main` nach, löst
   Konflikte, führt `pnpm install --frozen-lockfile` und das Gate aus.
7. **Aufräumen.** Umgesetzte Pläne entfernt sie. Reste archivierter Kindsessions räumt sie weg, einen Worktree erst
   nach der Prüfung auf ungesicherte Änderungen.

### 3. Branches

- Ein **Basisbranch** `feat/<thema>` hält den Koordinationsplan, die Teilpläne und alles, was nur zusammen live gehen
  kann. Er geht als Ganzes nach `main`.
- **Teile, die für sich nützlich sind**, zweigen von `main` ab und gehen einzeln nach `main`: kleine Deploys, kein
  langes Auseinanderlaufen gegen die Fixes auf `main`.
- Eine Kindsession arbeitet auf `feat/<kürzel>-<teil>`. Der Basisbranch übernimmt per `git merge --ff-only`.
- Keine Merge-Commits, nur Fast-forward und Rebase.

### 4. Die Kindsession

1. **Ein Teilplan, ein Worktree.** Genau ein freigegebener Teilplan, ein eigener Worktree, Branch
   `feat/<kürzel>-<teil>`. Erster Commit ist der Plan (`git show <basisbranch>:plans/<plan>.md`).
2. **PIV.** `/implement` autonom, wenn der Plan keine geschützten Pfade berührt, sonst `--step` oder von Hand; danach
   `/validate` und `/review`. Sie plant nicht neu. Weicht etwas vom Plan ab, meldet sie es und wartet.
3. **Keine weiteren Sessions.** Sub-Agents innerhalb der Session (etwa `code-reviewer`) sind erlaubt.
4. **Nur die koordinierende Session als Gegenüber**, per `SendMessage`: Fragen, Circuit-Breaker, Abschluss. Nicht mit
   dem User.
5. **Geschützte Pfade:** Diff vorlegen, auf OK warten, dann committen.
6. Kein Merge, kein Push, kein Release, kein Deploy.
7. **Abschluss:** Vault-Notes und Lessons zuerst, den umgesetzten Plan per letztem Commit entfernen, auf die Basis
   rebasen (`main` oder Basisbranch), Gate grün im Worktree, dann melden: Branch, Commits, Bericht, was nicht belegt
   ist, ob eine neue Brücke oder ein Deploy-Schritt nötig ist. Danach keine Commits mehr.
8. **Nach „übernommen“:** Berichte in `reports/` des Haupt-Checkouts kopieren, Branch und Worktree löschen, sich
   archivieren.

### 5. Parallel

Parallel läuft nur, was sich nicht berührt. Zur selben Zeit ändert höchstens eine Kindsession das Schema einer App
(die Dev-Datenbank ist geteilt). Ports von Dev-Server und Skriptprüfung spricht die koordinierende Session ab. Die
Dev-Datenbank wird nie zurückgesetzt. Zwei bis drei Kindsessions zugleich, nicht mehr.

### 6. Grundsätze

Diese Grundsätze hat der User für das erste koordinierte Vorhaben festgelegt. Sie gelten für jedes Vorhaben und
stehen im Koordinationsplan oben, ergänzt um die eigenen des Vorhabens:

- **Entfernen entfernt nur das, was man entfernt.** Abhängige Daten bleiben stehen.
- **Immer das Maximum an Daten speichern.** Gespeichert wird, was die Quelle hergibt; gewertet wird in der Ansicht.
- **An dem orientieren, was es schon gibt.** Bedienung und Modell knüpfen an Vorhandenes an, statt Neues zu erfinden.
- **Konsistenz, wo immer sie möglich und sinnvoll ist** (User, 27. Oktober 2026): Gleiches sieht gleich aus und steht
  an derselben Stelle, unabhängig von Herkunft oder Detailtiefe. Ein Zustand unterscheidet sich im Inhalt (Wert oder „–“
  mit Grund), nicht im Aufbau der Seite. Abweichen nur mit Grund, der im Plan steht.

## Alternativen

- _Alles in einer Session:_ verworfen. Der Kontext läuft über Erkundung, Code und Gates voll, parallele Teile gehen
  nicht, und Planen und Bauen vermischen sich.
- _Kindsessions mit eigenen Kindsessions:_ verworfen. Der Überblick zerfällt, Rückfragen laufen über mehrere Ebenen,
  und niemand hält den Stand des Ganzen.
- _Nur Sub-Agents statt Kindsessions:_ verworfen. Ein Sub-Agent endet mit dem Turn, hat keinen eigenen Worktree, kann
  nicht interaktiv an geschützten Pfaden warten und ist für den User nicht zu öffnen oder zu steuern. Für Erkundung
  und Review bleiben Sub-Agents das richtige Werkzeug.

## Folgen

- Skill `/coordinate` (`.claude/skills/coordinate/SKILL.md`) beschreibt den Ablauf der koordinierenden Session, mit
  einer Vorlage für den Auftrag an eine Kindsession und der Checkliste „Branch übernehmen“.
- Root-`CLAUDE.md`: Hard Rule 7 nennt den Modus, der Harness-Abschnitt den Skill.
- **Schärft [[adr-024]]:** Die Worktree-Wahl der Hauptsession ist im koordinierten Modus fest getroffen: kein Worktree
  für die koordinierende Session, je einer für jede Kindsession.
- **Schärft [[adr-023]]:** Der Autopilot bleibt an die Plan-Freigabe gebunden. Geschützte Pfade bekommen zusätzlich
  eine zweite Prüfung durch die koordinierende Session vor dem Commit.
- **Schärft [[adr-018]]:** Sub-Agents bleiben für Erkundung und Review. Wo ein Teil eine eigene Lebensdauer, einen
  eigenen Branch und eigene Rückfragen braucht, tritt eine Kindsession an ihre Stelle.
- Der Koordinationsplan ist ein Plan wie jeder andere ([[adr-018]]): Ist das Vorhaben fertig, wird er gelöscht. Was
  dauerhaft gilt, steht im Vault.
- Diese ADR entstand selbst in einer Kindsession, von Hand, weil sie `.claude/` und `vault/decisions/` berührt.
